# Гайд для нового участника команды

Этот документ объясняет, как начать работу с проектом: от клонирования
репозитория до взятия задачи в YouTrack и передачи изменений на ревью.

## 1. Что мы разрабатываем

Мы разрабатываем backend-сервис, который собирает вакансии разработчиков из
HH.ru, сохраняет их в PostgreSQL и предоставляет данные через REST API.

Основной стек: Python 3.14, uv, FastAPI, PostgreSQL, SQLAlchemy 2.x, aiohttp /
asyncio, APScheduler и pytest. Общее описание проекта находится в
[README](../README.md).

## 2. Что установить до начала работы

Нужны Git, Python 3.14, uv, Docker Desktop и доступ к репозиторию GitHub и
проекту YouTrack.

На Windows установите [Git for Windows](https://git-scm.com/downloads/win).
Команды из этого гайда можно выполнять в PowerShell. Для команд с SSH ниже
приведены отдельные варианты для Windows.

Проверить установку:

```bash
git --version
python3 --version
uv --version
```

На Windows в PowerShell вместо `python3 --version` используйте:

```powershell
py -3.14 --version
```

Если Python имеет версию ниже 3.14, установите Python 3.14 и настройте его для
работы с uv.

## 3. Клонирование репозитория

Есть два варианта. Для первого запуска проще использовать HTTPS: SSH-ключ ещё
не нужен.

### Вариант A. HTTPS без SSH-ключа

```bash
git clone https://github.com/StormHuracan/job-aggregator.git
cd job-aggregator
git checkout main
git pull origin main
git status
```

Перед началом работы в выводе `git status` не должно быть чужих изменений.

При первом `git push` GitHub не принимает пароль от аккаунта. Терминал может
открыть браузер для авторизации в GitHub. Завершите авторизацию в браузере и
вернитесь в терминал.

### Вариант B. SSH-ключ для постоянной работы

SSH удобнее для постоянной работы: после настройки `git pull` и `git push` не
будут каждый раз запрашивать авторизацию в браузере.

#### Шаг 1. Проверить существующий SSH-ключ

На macOS или Linux выполните:

```bash
ls -al ~/.ssh
```

Если уже есть файлы `id_ed25519` и `id_ed25519.pub`, можно использовать этот
ключ. Файл с расширением `.pub` — публичный ключ, его можно добавлять в GitHub.
Файл без расширения — приватный ключ, его никому нельзя отправлять.

На Windows в PowerShell выполните:

```powershell
Get-ChildItem $env:USERPROFILE\.ssh
```

#### Шаг 2. Создать новый ключ, если его нет

Замените почту на почту своего GitHub-аккаунта:

```bash
ssh-keygen -t ed25519 -C "your-github-email@example.com"
```

Когда команда спросит путь, нажмите Enter, чтобы использовать стандартный путь:

```text
~/.ssh/id_ed25519
```

Можно задать passphrase: это пароль для защиты ключа на вашем компьютере.

На Windows в PowerShell используется та же команда:

```powershell
ssh-keygen -t ed25519 -C "your-github-email@example.com"
```

Стандартный путь на Windows:

```text
C:\Users\ваше-имя\.ssh\id_ed25519
```

#### Шаг 3. Добавить ключ в ssh-agent

Запустите ssh-agent:

```bash
eval "$(ssh-agent -s)"
```

Добавьте ключ:

```bash
ssh-add ~/.ssh/id_ed25519
```

На Windows в PowerShell сначала включите системный ssh-agent. PowerShell нужно
открыть **от имени администратора**:

```powershell
Get-Service ssh-agent | Set-Service -StartupType Automatic
Start-Service ssh-agent
```

Затем откройте обычный PowerShell и добавьте ключ:

```powershell
ssh-add $env:USERPROFILE\.ssh\id_ed25519
```

#### Шаг 4. Скопировать публичный ключ

На macOS:

```bash
pbcopy < ~/.ssh/id_ed25519.pub
```

На Linux можно вывести ключ и скопировать его вручную:

```bash
cat ~/.ssh/id_ed25519.pub
```

На Windows в PowerShell ключ можно сразу скопировать в буфер обмена:

```powershell
Get-Content $env:USERPROFILE\.ssh\id_ed25519.pub | Set-Clipboard
```

#### Шаг 5. Добавить ключ в GitHub

1. Откройте GitHub.
2. Нажмите на аватар справа вверху.
3. Откройте **Settings**.
4. Откройте **SSH and GPG keys**.
5. Нажмите **New SSH key**.
6. Укажите понятное название, например `Daniil MacMini`.
7. Вставьте скопированный публичный ключ.
8. Нажмите **Add SSH key**.

#### Шаг 6. Проверить подключение

```bash
ssh -T git@github.com
```

При первом подключении SSH может спросить подтверждение адреса GitHub. Введите
`yes`. Успешная проверка завершается приветствием от GitHub.

#### Шаг 7. Переключить уже склонированный репозиторий на SSH

Если репозиторий был склонирован по HTTPS, это не нужно клонировать заново.
Внутри каталога проекта выполните:

```bash
git remote set-url origin git@github.com:StormHuracan/job-aggregator.git
git remote -v
```

В выводе у `origin` должен быть адрес, начинающийся с:

```text
git@github.com:
```

## 4. Установка зависимостей

```bash
uv sync
cp .env.example .env
```

`uv sync` создаст локальное окружение `.venv`. Файл `.env` и каталог `.venv`
нельзя добавлять в Git.

## 5. Первый запуск и проверка

На текущем этапе backend можно запустить без подключения к базе данных:

```bash
uv run uvicorn job_aggregator.main:app --reload
```

В другом терминале проверьте endpoint работоспособности:

```bash
curl http://127.0.0.1:8000/health
```

Ожидаемый ответ:

```json
{"status": "ok"}
```

Запустите тесты:

```bash
uv run pytest
```

Если тесты падают до ваших изменений, сообщите об этом тимлиду и приложите текст
ошибки.

## 6. Как взять задачу в YouTrack

1. Откройте проект **Job Aggregator** в YouTrack.
2. Выберите задачу без незавершённых зависимостей.
3. Прочитайте полностью: «Что нужно сделать», «Основание», «Зависимости» и
   «Критерии приёмки».
4. Убедитесь, что задачу не выполняет другой участник.
5. Назначьте задачу на себя или сообщите тимлиду, что берёте её — по процессу
   команды.
6. Если описание непонятно, задайте вопрос в комментарии YouTrack-задачи или в
   командном чате. Не угадывайте требования.

Не берите заблокированную задачу без согласования с тимлидом, кроме случаев,
когда её можно выполнить через fake/mock-реализацию.

## 7. Создание рабочей ветки

Одна задача — одна ветка. Имя ветки содержит номер задачи и краткое название:

```bash
git checkout -b feature/JA-16-vacancy-model
```

Для исправления ошибки используйте `fix`:

```bash
git checkout -b fix/JA-42-vacancy-filter
```

Не работайте прямо в `main`.

## 8. Как писать код

Перед началом прочитайте [README.md](../README.md), описание задачи в YouTrack
и существующий код в изменяемом модуле.

Основные правила:

- используйте type hints;
- публичные классы и методы снабжайте полезными docstring на русском;
- пишите комментарии на русском только для неочевидных решений;
- не меняйте несвязанные части проекта;
- не добавляйте инфраструктуру без явной необходимости;
- не храните секреты в коде или логах;
- пишите тесты для новой логики.

## 9. Работа с внешними API

Endpoint-ы и параметры берите из официальной документации выбранного внешнего
API. Интеграции должны быть изолированы в отдельном слое приложения, чтобы
роуты FastAPI и бизнес-логика не зависели напрямую от сторонних библиотек или
формата внешнего ответа.

В тестах внешние API нужно заменять mock/fake-ответами. Тесты не должны зависеть
от реального сетевого доступа и действующих токенов.


## 10. Как тестировать задачу

Минимально перед передачей задачи на ревью:

```bash
uv run pytest
```

Если задача добавляет API, дополнительно проверьте endpoint через FastAPI docs
или HTTP-клиент. В тестах внешних интеграций используйте mock/fake-ответы, а не
реальные запросы к HH.ru.

## 11. Коммиты

Перед коммитом:

```bash
git status --short
git diff --check
```

В коммит должны попасть только файлы вашей задачи. Сообщения коммитов пишутся в
формате Conventional Commit и описывают завершённое изменение в прошедшем
времени:

```text
(feat): Добавлена модель вакансии
(fix): Исправлена фильтрация по компании
(test): Добавлены тесты клиента HH.ru
(docs): Обновлена инструкция запуска
```

Пример:

```bash
git add <нужные-файлы>
git commit -m "(feat): Добавлена модель вакансии"
```

Не добавляйте в коммит `.env`, `.venv`, access token, refresh token, временные
файлы и чужие незавершённые изменения.

## 12. Передача задачи на ревью

1. Проверьте все критерии приёмки в YouTrack.
2. Запустите тесты.
3. Убедитесь, что рабочее дерево содержит только ожидаемые изменения.
4. Отправьте ветку:

   ```bash
   git push -u origin <имя-ветки>
   ```

5. Создайте Pull Request в `main`.
6. В описании Pull Request укажите номер задачи, список изменений, выполненные
   проверки и известные ограничения.
7. Изменяйте статус задачи в YouTrack по процессу команды.

Пример описания Pull Request:

```text
Связано с JA-16.

Что сделано:
- добавлена модель вакансии;
- добавлено уникальное ограничение по источнику и внешнему ID;
- добавлены тесты сохранения модели.

Проверки:
- uv run pytest
```

## 13. Когда нужно спросить тимлида

Спросите до начала изменений, если задача требует новую инфраструктуру, реальный
токен внешнего API, изменение схемы базы без выбранного способа миграций,
изменение общего контракта между модулями или противоречит README либо
AGENTS.md.

Это нормально: лучше уточнить вопрос заранее, чем переделывать большую часть
задачи после ревью.
