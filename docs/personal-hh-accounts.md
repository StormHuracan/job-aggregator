# Персональные подключения HH.ru

`HHAccount` в `job_aggregator.db.models.hh_account` хранит один набор токенов
на `User.id`. `HHAccountRepository` в `job_aggregator.db.repositories.hh_account`
предоставляет `get_by_user_id(user_id)` и `save(user_id, HHAccountTokenData)`.

`save()` возвращает `True` при создании или изменении любого token-поля,
`False` — при полном совпадении. Если пользователь отсутствует, выбрасывает
`ValueError("Пользователь не найден")` до записи токенов. Метод вызывает
`flush()`, но не commit/rollback. Блокировка строки `User` действует до
завершения транзакции вызывающим кодом; поэтому также защищена конкурентная
первая вставка. Все writers должны использовать этот контракт.

Срок токенов — timezone-aware UTC. Модель не выводит токены в `repr`,
репозиторий не логирует их. Engine скрывает bind-параметры в текстах SQL-ошибок.
ORM-объект содержит секреты и не предназначен для
сериализации в HTTP-ответ. Публичные schemas продолжают возвращать только статус.

## Переход

Применить обычную миграцию `uv run alembic upgrade head`.
Ревизия `b62a19c4d801` создаёт `hh_accounts` поверх схемы
`f31a8b7d4c2e`. Таблица `hh_account_tokens` и её данные сохраняются.
Определить владельца singleton-токенов нельзя, поэтому автоматически они
не копируются: пользователи проходят OAuth повторно после переключения callback.

Существующий `TokenService` и singleton endpoint не переключаются этой задачей.
Персональное подключение используют следующие задачи JA-31 и JA-56.
Downgrade новой миграции удаляет персональные подключения; legacy-таблица
остаётся нетронутой.

## Проверки

Общие проверки выполняются через `uv run pytest`. Для concurrency и настоящей
миграции задать `TEST_DATABASE_URL` отдельной тестовой PostgreSQL, затем:

```bash
uv run pytest tests/db/repositories/test_hh_account_postgres.py tests/db/test_hh_account_migration_postgres.py
```

Эти тесты пересоздают схему тестовой базы. Миграционный тест дополнительно
сбрасывает `alembic_version`; рабочую базу разработчика указывать нельзя.
