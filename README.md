# job-aggregator

`job-aggregator` — backend-сервис для агрегации вакансий разработчиков с HH.ru.

Сервис собирает вакансии из внешних источников, сохраняет их в PostgreSQL без
дубликатов, обновляет уже известные вакансии и предоставляет данные через
REST API.

## MVP

В рамках MVP проект должен уметь:

- запускать FastAPI-приложение;
- подключаться к PostgreSQL через настройки окружения;
- собирать вакансии разработчиков из HH.ru;
- сохранять вакансии через SQLAlchemy 2.x;
- предотвращать дубли по внешнему идентификатору вакансии;
- обновлять изменившиеся данные уже сохранённых вакансий;
- отдавать сохранённые вакансии через REST API;
- поддерживать фильтрацию и пагинацию;
- запускать сбор вручную для демонстрации и по расписанию;
- покрывать основную логику тестами без реальных сетевых запросов.

Не входит в MVP, если не останется времени: автоотклики, обновление резюме,
уведомления, AI-фильтрация, статистика рынка и административный интерфейс.

## Архитектура

Проект строится как простое слоистое приложение. Работа с HH.ru намеренно
изолирована в отдельном слое интеграции:

```text
роуты FastAPI
  -> сервисы приложения
    -> репозитории и модели базы данных
    -> интеграции с внешними API
      -> адаптер HH.ru
```

Основные зоны ответственности:

- `api` — HTTP-роуты FastAPI;
- `core` — конфигурация и логирование;
- `db` — подключение к базе данных, сессии SQLAlchemy и базовая metadata;
- `integrations` — клиенты внешних API;
- `services` — бизнес-логика приложения.

Бизнес-логику не стоит размещать прямо в роутерах, если она становится
нетривиальной. Интеграции с внешними API должны быть изолированы от API-слоя и
тестироваться с моками.

### Правило использования hh-applicant-tool

Сторонний проект `hh-applicant-tool` можно использовать только внутри модуля
`job_aggregator.integrations.hh`.

Разрешённая идея использования:

- `HHClient` — обёртка над запросами к HH API;
- `HHOAuthClient` — обёртка над OAuth-авторизацией HH.ru.

Остальной код проекта не должен импортировать `hh_applicant_tool` напрямую.
Запрещено строить бизнес-логику проекта вокруг auto-apply, UI, storage или CLI
из стороннего проекта.

Это ограничение проверяется тестом:

```bash
uv run pytest tests/test_hh_applicant_tool_imports.py
```

Важно: на момент подготовки каркаса у `hh-applicant-tool` есть ограничение по
версии Python, поэтому импорт выполняется лениво внутри слоя интеграции. Если
библиотека недоступна в окружении, слой интеграции вернёт понятную ошибку.

## Локальный запуск

```bash
uv sync
cp .env.example .env
uv run uvicorn job_aggregator.main:app --reload
```

Для локального запуска нужен PostgreSQL, доступный по `DATABASE_URL` из `.env`.

Проверка работоспособности приложения:

```bash
curl http://127.0.0.1:8000/health
```

Ожидаемый ответ:

```json
{"status": "ok"}
```

## Настройки окружения

Пример настроек находится в `.env.example`.

Основные переменные:

- `APP_NAME` — имя приложения;
- `APP_ENV` — окружение запуска;
- `LOG_LEVEL` — уровень логирования;
- `DATABASE_URL` — строка подключения к PostgreSQL;
- `HH_CLIENT_ID` — идентификатор OAuth-приложения HH.ru;
- `HH_CLIENT_SECRET` — секрет OAuth-приложения HH.ru;
- `HH_REDIRECT_URI` — callback URL для авторизации HH.ru;
- `COLLECTION_DEFAULT_QUERY` — поисковый запрос по умолчанию;
- `COLLECTION_DEFAULT_AREA` — регион HH.ru по умолчанию;
- `COLLECTION_PAGES_LIMIT` — ограничение количества страниц при сборе;
- `SCHEDULER_ENABLED` — включение планировщика;
- `SCHEDULER_INTERVAL_MINUTES` — интервал запуска планировщика.

Реальные секреты, токены и пароли нельзя коммитить в репозиторий.

## Тесты

```bash
uv run pytest
```

Тесты внешних интеграций должны использовать моки. Тестовый прогон не должен
зависеть от доступности реальных внешних API.
