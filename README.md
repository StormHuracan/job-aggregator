# job-aggregator

`job-aggregator` — backend-сервис для агрегации вакансий разработчиков с HH.ru.

Сервис собирает вакансии из внешних источников, сохраняет их в PostgreSQL без дубликатов, обновляет уже известные вакансии и предоставляет данные через REST API.

## MVP

В рамках MVP проект должен уметь:

- запускать FastAPI-приложение;
- подключаться к PostgreSQL через настройки окружения;
- собирать вакансии разработчиков с HH.ru;
- сохранять вакансии через SQLAlchemy 2.x;
- предотвращать дубли по внешнему идентификатору вакансии;
- обновлять изменившиеся данные уже сохранённых вакансий;
- отдавать сохранённые вакансии через REST API;
- поддерживать фильтрацию и пагинацию;
- запускать сбор вручную для демонстрации и по расписанию;
- покрывать основную логику тестами без реальных сетевых запросов.

Не входит в MVP, если не останется времени: автоотклики, уведомления, AI-фильтрация, статистика рынка и административный интерфейс.

## Архитектура

Проект строится как простое слоистое приложение:

```text
HTTP-роуты FastAPI
  -> сервисы приложения
    -> репозитории и PostgreSQL
    -> интеграция с HH.ru
  -> response schemas

планировщик
  -> сервисы приложения
```

Основные зоны ответственности:

- `api` — HTTP-роуты FastAPI;
- `core` — конфигурация и логирование;
- `db` — подключение к базе данных, сессии SQLAlchemy и базовая metadata;
- `integrations` — клиенты внешних API;
- `services` — бизнес-логика приложения;
- `schemas` — публичные request/response-модели API;
- `scheduler` — запуск сервисов по расписанию.

Бизнес-логику не стоит размещать прямо в роутерах, если она становится нетривиальной. Интеграции с внешними API должны быть изолированы от API-слоя и тестироваться с моками.

`repositories` содержат только операции с PostgreSQL для конкретных сущностей; общий generic repository не используется. `services` не зависят от FastAPI и могут тестироваться с fake-провайдерами HH.ru без сети.

## Локальный запуск

### Backend и PostgreSQL через Docker Compose

Нужны Docker с Compose. Python и uv на компьютере для этого варианта не нужны.

Если `.env` ещё нет, создайте его из примера. Существующий файл не перезаписывайте. Для старого `.env` добавьте `COMPOSE_DATABASE_URL` по примеру из `.env.example`.

```bash
test -f .env || cp .env.example .env
docker compose up --build -d --wait
curl http://127.0.0.1:8000/health
```

Compose ждёт готовности PostgreSQL. Backend выполняет `alembic upgrade head`, затем запускает API одним worker без reload. При ошибке миграции API не запускается: причину можно посмотреть через `docker compose logs backend`. Для старой базы сначала проверьте раздел миграций ниже.

Ожидаемый ответ health check:

```json
{"status": "ok"}
```

Swagger доступен по адресу http://127.0.0.1:8000/docs. Без `HH_REDIRECT_URI` форма использует вход HH по SMS/email-коду через встроенный клиент SDK. Для собственного OAuth-приложения заполните `HH_CLIENT_ID`, `HH_CLIENT_SECRET` и `HH_REDIRECT_URI`. Health/docs не подтверждают доступность самого HH. Frontend запускается отдельно по [его инструкции](frontend/README.md).

`DATABASE_URL` используется для запуска с компьютера, а `COMPOSE_DATABASE_URL` — внутри backend-контейнера. В контейнерном URL хост — `postgres`, порт — `5432`. При изменении `POSTGRES_DB`, `POSTGRES_USER` или `POSTGRES_PASSWORD` обновите контейнерный URL; спецсимволы логина/пароля в URL кодируются percent-encoding. Изменение credentials в `.env` не меняет уже созданную базу в volume.

Порты компьютера задаются `BACKEND_PORT` и `POSTGRES_PORT` (по умолчанию 8000 и 5432). При изменении порта БД измените также host `DATABASE_URL`; порт `COMPOSE_DATABASE_URL` остаётся 5432. При другом backend-порте понадобится согласовать Vite proxy с адресом backend.

Полезные команды:

```bash
docker compose logs -f backend
docker compose exec backend alembic current
docker compose exec backend alembic check
docker compose down
```

Обычный `down` сохраняет данные в volume `pgdata`; `down -v` удаляет их. При обновлении кода снова выполните `docker compose up --build -d --wait`.

Автосбор включается настройками приложения после регистрации job; контейнер сам по себе не добавляет отсутствующую бизнес-логику scheduler.

### Backend на компьютере, PostgreSQL в Docker

Для этого варианта нужны Python, uv и Docker с Compose.

Если `.env` ещё не существует, создайте его. Существующий файл не перезаписывайте.

```bash
uv sync
test -f .env || cp .env.example .env
```

Настройте `DATABASE_URL` в `.env`. Для этого варианта используется адрес PostgreSQL с компьютера, а не адрес контейнера `postgres`. Если локальный порт PostgreSQL занят, можно использовать другой свободный порт и согласовать его с `POSTGRES_PORT` и `DATABASE_URL`.

Запустите PostgreSQL и проверьте состояние контейнера:

```bash
docker compose up -d postgres
docker compose ps
```

Убедитесь, что PostgreSQL перешёл в состояние `healthy`. Если контейнер не запустился, посмотрите логи:

```bash
docker compose logs postgres
```

Для этого варианта нужна пустая локальная база PostgreSQL либо база, схема которой уже корректно переведена на Alembic. Не запускайте миграции вслепую поверх базы, созданной старой версией приложения через `create_all()`.

Примените миграции, затем запустите приложение:

```bash
uv run alembic upgrade head
uv run uvicorn --app-dir src job_aggregator.main:app --reload
```

В другом терминале проверьте работоспособность приложения:

```bash
curl http://127.0.0.1:8000/health
```

Ожидаемый ответ:

```json
{"status": "ok"}
```

Для обычного запуска приложения и тестов OAuth-токены HH.ru не нужны. Реальные запросы к HH.ru требуются для проверки интеграции с сервисом. Планировщик по умолчанию отключён (`SCHEDULER_ENABLED=False`).

Запуск API не создаёт таблицы автоматически: схема базы обновляется через Alembic.

## Миграции базы данных

Схема PostgreSQL изменяется через Alembic. Адрес базы берётся из `DATABASE_URL`, как и у приложения. Запуск API больше не создаёт таблицы автоматически.

Применить все миграции к локальной базе:

```bash
uv run alembic upgrade head
```

Миграция `b62a19c4d801` добавляет персональные HH-подключения в `hh_accounts`. Старая таблица `hh_account_tokens` и её данные сохраняются без переноса: определить владельца старых токенов нельзя. После переключения OAuth callback на персональные подключения потребуется повторный вход через HH.ru.

### Переход с базы, созданной через create_all

Начальная миграция создаёт таблицы, поэтому её нельзя просто применить поверх уже существующих `hh_account_tokens`, `saved_searches` и `vacancies`.

Перед переходом остановите приложение, проверьте адрес выбранной БД и сделайте резервную копию данных и схемы.

- Если прежние данные не нужны для текущего запуска, создайте новую пустую базу, укажите её в `DATABASE_URL` и выполните `uv run alembic upgrade head`. Старую базу сохраните: удалять её для перехода не требуется.
- Если нужно продолжать работу с прежней базой, сначала сравните её схему с `alembic/versions/a87b31f96164_initial_schema.py`. Проверьте все колонки, типы, nullable, первичные ключи, ограничения и server defaults. Особое внимание уделите `singleton` и его unique constraint: `create_all()` не добавляет новые колонки и ограничения в уже существующие таблицы. Для сравнения можно применить миграцию к отдельной пустой БД и сопоставить схемы.

**Только если существующая схема полностью соответствует начальной миграции**, отметьте эту конкретную ревизию как применённую:

```bash
uv run alembic stamp a87b31f96164
uv run alembic upgrade head
uv run alembic check
```

`stamp` записывает номер ревизии, но не создаёт и не исправляет таблицы. `alembic check` дополнительно проверяет различия с ORM-моделями, но не заменяет предварительное сравнение схем.

Если схема отличается или есть только часть таблиц, не выполняйте `stamp`: нужен отдельный план приведения схемы или переноса данных в новую базу. Команды `downgrade base` и удаления таблиц не являются способом безопасного перехода — они удаляют данные.

### Новые изменения схемы

Создать новую ревизию по изменениям моделей:

```bash
uv run alembic revision --autogenerate -m "Описание изменения"
```

Перед коммитом проверьте сгенерированный файл в `alembic/versions/`: autogenerate создаёт черновик миграции и может ошибиться, например при переименовании колонок.

## Настройки окружения

Пример настроек находится в `.env.example`.

Основные переменные:

- `APP_NAME` — имя приложения;
- `APP_ENV` — окружение запуска;
- `LOG_LEVEL` — уровень логирования;
- `DATABASE_URL` — строка подключения к PostgreSQL.

HH.ru:

- `HH_CLIENT_ID` — идентификатор приложения, зарегистрированного на HH.ru;
- `HH_CLIENT_SECRET` — секретный ключ приложения HH.ru;
- `HH_REDIRECT_URI` — адрес, на который HH.ru возвращает пользователя после авторизации через OAuth;
- `HH_ALLOW_TOKEN_REFRESH` — разрешить автоматическое обновление токена доступа HH.ru, по умолчанию `false`.

Без `HH_REDIRECT_URI` frontend использует вход по одноразовому SMS/email-коду: `GET /auth/hh/options`, затем `POST /auth/hh/otp/start`, `/otp/verify`, при необходимости `/otp/captcha`; `/otp/cancel` отменяет попытку. Код вводит сам пользователь в интерфейсе. OAuth-токены сохраняются только на сервере, cookie приложения выдаётся после успешного commit пользователя, подключения и сессии.

OTP-адаптер использует неофициальный web-протокол hh-applicant-tool 2.0.1: изменения сайта HH могут нарушить этот способ входа. Временный cookie jar изолирован для каждой попытки и живёт в памяти одного worker до 10 минут. После рестарта или смены worker вход нужно начать заново. Максимум пять проверок на попытку, отправка кода не чаще раза в минуту на логин, не более десяти запусков за десять минут с одного IP. Не передавайте код через чат или логи.

При заданном `HH_REDIRECT_URI` используется обычный OAuth.

Вход начинается через `GET /auth/hh/login`, HH.ru возвращает пользователя на `GET /auth/hh/callback?code=…&state=…`. Callback потребляет одноразовый state, сохраняет персональные `User`/`HHAccount` и серверную сессию и отвечает `303 /account`. Cookie `job_aggregator_session` имеет HttpOnly, SameSite=Lax, Path=/ и срок семь дней; вне `APP_ENV=local` используется Secure, поэтому нужен HTTPS.

Для локального frontend с Vite proxy callback должен возвращаться через тот же origin, например `http://127.0.0.1:5173/api/auth/hh/callback`, если этот адрес зарегистрирован для вашего приложения HH.ru. Не смешивайте `localhost` и `127.0.0.1`: cookie относится к выбранному хосту. Прямой callback на backend `:8000` перенаправит `/account` на backend, который не обслуживает SPA. При невалидном/повторном state возвращается 400; при ошибке HH или сохранения успешная cookie не выдаётся. Начните вход заново через `/auth/hh/login`. Код и state callback удаляются из стандартных access-логов приложения; при использовании внешнего reverse proxy его query-логи нужно настроить отдельно.

Сбор вакансий:

- `COLLECTION_DEFAULT_QUERY` — поисковый запрос по умолчанию для сбора вакансий, по умолчанию `python`;
- `COLLECTION_DEFAULT_AREA` — регион поиска HH.ru; пустое значение означает поиск по всем регионам;
- `COLLECTION_PAGES_LIMIT` — сколько страниц результатов собирать за один запуск, больше нуля, по умолчанию `5`.

Планировщик:

- `SCHEDULER_ENABLED` — включить автоматический сбор вакансий по расписанию, по умолчанию `false`;
- `SCHEDULER_INTERVAL_MINUTES` — интервал между запусками сбора в минутах, больше нуля, по умолчанию `60`.

При `SCHEDULER_ENABLED=true` приложение запускают одним worker-процессом и одной репликой. В каждом процессе работает свой планировщик, поэтому при нескольких процессах сбор вакансий будет запускаться по разу в каждом из них.

Пустое значение переменной в `.env` считается отсутствующим, поэтому используется значение по умолчанию.

Реальные секреты, токены и пароли нельзя коммитить в репозиторий.

## Проверки перед Pull Request

После выполнения [JA-55 — Добавить Ruff для проверки и форматирования кода](https://StackEight.youtrack.cloud/issue/JA-55) перед передачей изменений на ревью запускайте:

`ruff check` находит базовые ошибки и неиспользуемые импорты, а `ruff format --check` проверяет единый формат файлов. Если форматирование требует изменений, выполните `uv run ruff format .` и добавьте результат в свой коммит.
